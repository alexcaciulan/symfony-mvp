# LexRecovery. In-App Notifications Subsystem: Final Implementation Plan (decision-ready)

## 1. Executive Summary

The server-side foundation is strong and must be preserved, not rewritten. `NotificationDispatcher` (`src/Service/Notification/NotificationDispatcher.php`) today fans a single immutable `NotificationDispatch` DTO out to three fault-isolated, headless-safe channels (email, in-app DB row, Mercure toast), and `EmailNotificationSubscriber` already produces correct, fully translated dispatches for 8 trigger families. The `Notification` entity, `NotificationRepository` (currently only `countUnreadByUser` + `findRecentByUser`), `NotificationTableDefinition`, and an accessibility-correct `toast_controller.js` all exist. The plumbing to produce and store notifications is roughly 70% done. **Decision for this subsystem: drop the Mercure real-time channel and surface new notifications by lightweight client polling of the durable DB (see D6); the dispatcher keeps two durable channels, email + in-app row.** The Mercure hub may remain for other subsystems (wizard extraction progress), but the notification center no longer depends on it.

What is missing is the entire consumer surface and the breadth of coverage. There is no header bell, no unread badge, no dropdown, no mark-read / mark-all-read lifecycle (the entity has only a boolean `isRead`, no `readAt`; the repository has no mutation queries), and `NotificationsController` is a bare stub (verified: single `index()` returning a template). The removed Mercure toast channel was in fact broken today anyway (confirmed against `templates/base.html.twig` line ~146: the element binds `data-action="mercure:message@window->toast#show"`, which passes the raw `CustomEvent` to `show({message,variant})`; the destructure reads the Event object, `message` is `undefined`, and `show()` early-returns), so replacing it with polling loses nothing that works today. Coverage is also partial: only a subset of the 12 workflow places notify, all billing/dunning/payment/invoice flows bypass the dispatcher (email-only or silent), AI-extraction completion never persists an in-app row, and the portal flow persists an in-app row outside the dispatcher (`CaseMonitoringService::createNotification`, verified line 138 to 152) with hardcoded Romanian copy.

Beyond wiring, review surfaced four correctness defects that reshape the plan and must be designed in from the start, not patched later:

1. **Transition-level notifications, not place-entry.** The state machine (verified `config/packages/workflow.yaml`, 12 places / 14 transitions) has multiple transitions converging on one place. `RESPINSA` is reached by `respinge` (a first-instance OP rejection) and by `admite_cerere_anulare` (annulment admitted, order falls, case goes to common-law fond). `DEFINITIVA` is reached by `marcheaza_definitiva` (10-day annulment window lapsed) and by `respinge_cerere_anulare` (annulment rejected, ruling appealable). `EXECUTARE` is reached by `trece_la_executare` and by the self-loop `respinge_cerere_anulare_executare`. An `entered.PLACE` listener structurally cannot tell these apart, yet the copy for each branch is legally opposite. All copy-differentiated notifications must listen on `workflow.legal_case.completed.<transition>`.

2. **No flush inside a caller's transaction.** `persistInApp()` calls `$em->flush()` on the whole UnitOfWork (verified line 84). New producers (Netopia webhook handler, portal monitoring, extraction handler) call `dispatch()` while holding unrelated pending changes; a mid-handler flush commits them prematurely and breaks atomicity. The dispatcher must persist-without-flush and let the producer flush at its own boundary (or dispatch on a post-commit event).

3. **A real dedup key with a DB unique constraint.** The two highest-risk new producers run under retry (Messenger retries the extraction handler; Netopia can resend the same IPN). A soft guard is insufficient; a nullable `dedup_key` column with a unique index is required.

4. **Legally accurate, branch-specific copy for a lawyer audience.** Confirmed with counsel-grade care against CPC art. 1023 to 1024: the annulment-admitted branch takes the case out of LexRecovery scope, and the annulment-rejected branch produces an appealable ruling, so single generic "cerere respinsă" / "a devenit definitivă" copy would mislead. Copy for these branches is a legal-accuracy requirement and is documented as blocking for Phase C.

The plan closes these in a dependency chain (not independent islands): **A (foundation + correctness) then B (consumer surface) then {C (coverage), D (client polling)} then E (preferences)**. Only A is standalone; C and D deliver no lawyer-visible value until B exists; E needs B. A+B is the minimum viable shippable increment.

## 3. Architecture Decisions (decision-first)

Each decision lands as a short note in `docs/LexRecovery/` before its phase is coded. All notes and all translated strings are written with regular punctuation only (no em-dash), per project convention.

### D1. Schema: add `readAt` + `dedupKey` + indexes (migration required)
- Add `Notification.readAt: ?\DateTimeImmutable` (nullable). Keep `isRead` as the fast filter, but `readAt` is the honest cross-device "when read" source. `setIsRead(true)` sets `readAt = now()` if not already set; `setIsRead(false)` nulls it.
- Add `Notification.dedupKey: ?string(191)` with a **unique index** (D9). Null means "not deduplicated".
- Add composite indexes `(user_id, is_read)` and `(user_id, created_at)` for the count/list hot paths.
- No `updatedAt`. The vestigial `NotificationChannel::EMAIL` case stays as-is; a per-channel delivery log is out of scope (open question).
- Files: `src/Entity/Notification.php`, `migrations/VersionXXXX.php`. Ops: `make migrate` then `make restart`.

### D2. Replace free-string `type` with a `NotificationType` backed enum
- New `src/Enum/NotificationType.php`: `label()`, `icon()`, `tier()` (high/medium/low), `suppressible(): bool`. One case per matrix row that persists an IA row, keyed to the trigger not the place, e.g. `CASE_STATUS`, `CASE_ANNULMENT_ADMITTED`, `CASE_ANNULMENT_REJECTED`, `DEADLINE_ALERT`, `PRESCRIPTION_ALERT`, `MISSING_COMMUNICATION_DATE`, `PORTAL_EVENT`, `PORTAL_RULING_CONFIRMATION`, `PORTAL_QUERY_FAILED`, `EXTRACTION_DONE`, `EXTRACTION_FAILED`, `EXTRACTION_LOW_CONFIDENCE`, `PAYMENT_SUCCEEDED`, `PAYMENT_FAILED`, `SUBSCRIPTION_PAST_DUE`, `TOKEN_EXPIRED`, `INVOICE_ISSUED`, `SLOT_OVERAGE`, `TRIAL_STARTED`, `TRIAL_ENDING`, `TRIAL_EXHAUSTED`, `SECURITY_PASSWORD_CHANGED`, `ADMIN_INVOICE_SEND_FAILED`.
- Canonicalize the historical `portal_update` vs `portal_event` value on `portal_event`; the migration data-rewrites existing rows.
- `Notification.type` stays stored as `string(50)` but the setter accepts `NotificationType` and stores `->value`; `NotificationDispatch.type` becomes `NotificationType`. Typed contract for icons/labels/filters/preferences without a DB enum.
- Files: `src/Enum/NotificationType.php`, `src/Entity/Notification.php`, `src/Service/Notification/NotificationDispatch.php`, all call sites, migration.

### D3. Repository query additions
Add to `NotificationRepository` (keep `countUnreadByUser`, `findRecentByUser`):
- `findPaginatedByUser(User, int $limit, int $offset, ?bool $unreadOnly, ?NotificationType $type): Notification[]` (center list + "load more" + filters).
- `findOneByIdAndUser(int $id, User): ?Notification` (ownership-guarded fetch before mark-read).
- `markAllReadByUser(User): int` (single DQL `UPDATE ... SET is_read=true, read_at=:now WHERE user=:u AND is_read=false`; avoids N flushes).
- `findOneByDedupKey(string): ?Notification` (producer-side guard, complementing the DB unique index).
- Files: `src/Repository/NotificationRepository.php`, `tests/Repository/NotificationRepositoryTest.php`.

### D4. Thin controller endpoints
Expand `src/Controller/NotificationsController.php` (thin; delegate to new `NotificationCenterService`):
- `GET /notifications` (`app_notifications`): full list page, server-rendered partial + "load more", passes unread count.
- `GET /notifications/dropdown` (`app_notifications_dropdown`): dropdown panel partial (recent 10) for lazy bell open / Turbo refresh.
- `GET /notifications/unread-count` (`app_notifications_unread_count`): lightweight JSON `{count}` for badge reconciliation on navigation and after mark-read.
- `POST /notifications/{id}/read` (`app_notification_read`): CSRF + ownership guard, Turbo Stream (badge + row) or redirect fallback.
- `POST /notifications/read-all` (`app_notifications_read_all`): CSRF, bulk mark, Turbo Stream / redirect.
- All `IsGranted('IS_AUTHENTICATED_FULLY')`. Ownership check, mark, count live in `src/Service/Notification/NotificationCenterService.php`.

### D5. UI components (conservative, lawyer audience)
- **Header bell** in `templates/_topbar.html.twig` (+ mobile drawer equivalent): Preline `hs-dropdown` trigger, bell icon, unread badge (server-rendered initial count via `countUnreadByUser`, capped "9+"). `aria-label` carries the count, `aria-expanded`, and stable ids `#notification-bell-badge` and `#notification-list` on every authenticated page so the poller and the dropdown always have stable targets.

- **Empty states**: reuse `templates/components/EmptyState.html.twig` ("no notifications yet" and "all caught up").
- Read/unread: unread = bolded + left dot; read = muted. Non-color cue mandatory (a11y).
- Click-through: row/title links to `resourceLink`; clicking marks read.

### D6. Real-time surfacing: client polling (no Mercure for the notification center)
The notification center does not use Mercure. New notifications are surfaced by lightweight client polling against the durable DB, keeping the subsystem free of the Mercure hub, the JWT TTL refresh problem, and the private-topic auth mismatch. Mercure may remain for other subsystems (e.g. wizard extraction progress via `ExtractionMercurePublisher`); that is out of scope here.
- **Dispatcher drops to two channels.** Remove `publishToast()` and the `HubInterface` dependency from `NotificationDispatcher`; it fans out to email + in-app DB row only. `NotificationDispatch.variant` is retained (it drives the in-app row severity/icon and the optional client toast below). This also deletes the current fault-isolation branch for Mercure and its `MercureTokenService::userNotificationTopic` call.
- **Badge = polled unread count.** `notification_center_controller.js` polls `GET /notifications/unread-count` on an interval (default 45s), backing off when the tab is hidden (Page Visibility API) and refreshing immediately on `focus` and `turbo:load`. The initial value is server-rendered from `countUnreadByUser`, so the badge is correct on first paint without waiting for the first poll. The server stays authoritative; a missed tick self-heals on the next one, and the badge also reconciles right after any mark-read.
- **Dropdown = lazy fetch on open.** Opening the bell issues `GET /notifications/dropdown` (D4), so the recent list is always fresh with no background stream, no client-side row templating, and no prepend logic.
- **Optional toast on delta (client-side, no server push).** If the polled count rose since the last tick, the controller may raise a local toast for high/medium-tier items by reading the newest rows from the dropdown payload (tier is carried per row). This is optional polish; the badge alone is sufficient. Low-tier flows never toast.
- **Own-action feedback is unchanged and needs no polling.** Feedback for the user's own request (submit, upload) is already server-rendered via `turbo-stream` in the HTTP response (e.g. `templates/case/_step0_upload_stream.html.twig`), independent of the notification center.
- **Residual Mercure note (out of scope, track separately):** the broken Mercure-to-toast bridge in `templates/base.html.twig` line ~146 (`event.detail.data` not unwrapped) only matters for any toast still pushed through Mercure by `ToastService`. It is no longer on the notification-center critical path; fix or retire it when the remaining `ToastService`/Mercure usage is revisited.
- **Cost:** `/notifications/unread-count` is a single indexed `COUNT` (D1 index `(user_id, is_read)`). At a 45s interval, even hundreds of concurrent lawyer tabs generate negligible load, and hidden tabs stop polling entirely.
- Files: `src/Service/Notification/NotificationDispatcher.php` (remove hub + `publishToast`), `assets/controllers/notification_center_controller.js` (poller), `templates/_topbar.html.twig` (server-rendered initial badge). No `MercureTokenService`, no `composer.json`/`importmap.php` changes for this subsystem.

### D7. Producer wiring without bloating one subscriber; transition-level listeners
One choke point (the dispatcher), no second manual-persist path. Split producers by domain, each `final`, `#[AsEventListener]`, depending only on `NotificationDispatcherInterface` + translator + urlgen:
- **Case/workflow** (`EmailNotificationSubscriber`, may rename to `CaseNotificationSubscriber`): **listen on `workflow.legal_case.completed.<transition>`, not `entered.PLACE`**, wherever copy differs by branch (verified necessary: `RESPINSA`, `DEFINITIVA`, `EXECUTARE` each have divergent transitions). Add the uncovered transitions (rows 2b, 6b, 12, 13, 14, 14b, 22, 23, 24) as thin handlers, each passing a branch-specific `NotificationType` + translator keys. Places reached by a single transition may keep a simpler handler.
- **Billing** (`src/EventSubscriber/BillingNotificationSubscriber.php`, new): route dunning / past-due / token-expired / renewal-success / invoice-issued / slot-overage / trial / manual-checkout through the dispatcher. Billing services emit domain events or call the dispatcher directly with the user resolved from `Subscription`/`Invoice` (headless-safe; never `ToastService`).
- **Extraction** (`src/EventSubscriber/ExtractionNotificationSubscriber.php`, new): on `DataExtractedEvent`, persist a durable IA row on completion (row 32), failure (row 20), and low-confidence-fields (row 31). The existing wizard-scoped progress toast stays.
- **Portal:** delete `CaseMonitoringService::createNotification` (verified line 138 to 152) and flip `PortalEventDetectedEvent` handling to `persistInApp: true` (single translated write). Add the `PORTAL_RULING_CONFIRMATION` action-required dispatch where `MonitoringEventApplier` proposes a sensitive transition (row 5), deep-linking to the manual-confirm UI from Pas 7.2. Add the after-N-failures warning (row 29).
- **Security:** password-changed notification (row 21) from `ProfileController`/`ResetPasswordController`; see D11 for session invalidation.

### D8. Fix the dunning email template-path bug during consolidation
`SubscriptionRenewalService` line 117 references `htmlTemplate('email/subscription_action_required.html.twig')` (singular) but the file is `templates/emails/subscription_action_required.html.twig` (plural, verified present); the exception is swallowed, so no dunning email is delivered today. ### D9. Idempotency and dedup (real, not soft)
- Add `dedupKey` to `NotificationDispatch` and the `dedup_key` unique column (D1). Producers that run under retry (extraction Messenger handler, Netopia IPN/webhook) set a stable key (e.g. `payment:{providerTxnId}:{event}`, `extraction:{documentId}:{status}`, `portal:{caseId}:{portalEventId}`). `persistInApp()` guards with `findOneByDedupKey` and relies on the unique index as the hard backstop (catch the unique-violation, log, no-op).
- Flows without a natural id (bulk deadline cron) already carry upstream per-deadline flags; keep those and additionally set a date-bucketed key where cheap.

### D10. Persist-without-flush; flush at the producer boundary
`persistInApp()` must call `$this->em->persist($notification)` only, never `$this->em->flush()`. The producer owns the flush:
- Synchronous request producers: the request/kernel-terminate flush already covers it; where none exists, the producer flushes explicitly.
- Cron/worker producers (deadline, dunning, portal, extraction): flush at the handler boundary after their own domain writes, so a single transaction commits atomically.
- To preserve the current fault-isolation guarantee (one bad notification must not poison a caller), producers dispatching in a loop should either flush per iteration around a try/catch or, preferably, dispatch on a **post-commit** hook so notification persistence never rides inside the domain transaction. The decision note picks per-producer: webhook/monitoring use post-commit; simple request flows flush inline.
- Files: `src/Service/Notification/NotificationDispatcher.php`, each producer.

### D11. Admin/operator recipient surface (row 30) and security session handling (row 21)
- **Admin surface:** fiscal-invoice / SPV send failures are a compliance risk (a fiscal document silently stuck unsent). Define a concrete recipient: a real operations address from config (replace the placeholder `admin@example.com`) plus an in-app row targeted at users holding `ROLE_ADMIN`, surfaced in the same center. `ADMIN_INVOICE_SEND_FAILED` is non-suppressible for admins. If no ops address is provisioned at implementation time, the row is still persisted for admins and the email is a follow-up, not a blocker.
- **Password change (row 21):** the in-app notification is informational only (the actor is the logged-in party; the at-risk account is elsewhere). The load-bearing channel is the confirmation EMAIL to the account, and the plan additionally requires **invalidating other sessions** on password change (Symfony logout of other tokens / password-hash invalidation). This is a security requirement, not a notification nicety.

## 4. Preferences Design (Phase E, last)

Preset modes, not a granular per-type matrix. Legal-deadline, prescription, and payment-failure categories are non-suppressible (malpractice risk).

- **Model:** add `User.notificationMode` (`ALL` | `IMPORTANT_ONLY` | `DIGEST`) plus a small JSON map of channel opt-outs for suppressible tiers only. Start with the single field + JSON map to avoid a heavy entity; upgrade to a `NotificationPreference` entity later if needed.
- **Enforcement:** a thin `NotificationPolicy` service consulted by the dispatcher, per channel, before `sendEmail`/`persistInApp` (the two remaining channels), using `NotificationType::suppressible()` + `tier()` + the user's mode. The client toast is a view of the in-app row, so it is gated by the same policy (a suppressed in-app row is never polled, hence never toasts). `suppressible() === false` always fires on all channels regardless of mode.
- **Non-suppressible set (confirmed in the Phase E decision note before coding):** procedural deadline (row 3), prescription (row 4), deadline-approaching (rows 9, evaluate), missing-communication-date (row 10, evaluate for the same reason: it gates all derived-term calculation), payment failure / dunning (row 15), token expired (row 16), PAST_DUE gating (row 17), annulment-admitted enforcement warning (row 2b), sensitive portal ruling (row 5), admin invoice-send failure (row 30). The `IMPORTANT_ONLY`/`DIGEST` logic must never downgrade these.
- **Digest:** low-tier flows batched into a daily email digest (new cron `app:notification-digest`); in-app rows still persist immediately (the center is the durable surface).
- **UI location:** a "Notificări" tab in the existing profile/settings surface, not a top-level page.
- Files: `src/Entity/User.php` (+migration), `src/Enum/NotificationMode.php`, `src/Service/Notification/NotificationPolicy.php`, `src/Form/NotificationPreferenceType.php`, `src/Controller/ProfileController.php`, `templates/profile/notifications.html.twig`.
